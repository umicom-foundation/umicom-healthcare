01 · Recommended start

Product overview and decisions

Create Umicom Healthcare as a new Umicom application; retain the established Master Controller / Slave Controllers structure and a single Framework source of truth. Begin with one synthetic, non-urgent outpatient consultation that includes onboarding, profile, assessment, safety review, route assignment, clinician interaction, optional investigation, treatment sign-off, signed prescription draft, simulated fulfilment and timeline projection.

Umicom FrameworkReusable runtime + healthcare services
Healthcare ModuleThin product composition
Umicom ApplicationsSuperproject and binary suite
Umicom HealthcareProduct documentation + governance
Future-goal interpretation. Multi-region infrastructure, autonomous diagnosis/prescribing, full clinical interoperability, marketplaces, advanced ML, microservices and distributed event sourcing are treated as deferred roadmap candidates, not features to implement in the first release. Any autonomous clinical action would require its own high-assurance clinical and regulatory programme.

02 · Capability inventory

What Umicom Framework supports today

The inspected GitHub main branch confirms a CMake superproject with Framework and application submodules, a module registration helper, manifest-based product targets and a shared Framework GTK4 native host. The Framework header tree has application, data, security, messaging, integration, observability, resilience and UI namespaces. Design manuals describe broader services, but their actual clinical assurance and operating behaviour have not been validated by executing the full Framework checkout here.

03 · Source of truth

Clear ownership, no duplicated infrastructure

Medical Management ServicesPatients, profiles, encounters, clinicians

Keep medical management independent of journeys: one patient medical record may support general consultation, specialist referral and rehabilitation without separate copies of a patient/profile implementation. Routing operates on queue assignments and clinical-service eligibility only; its public type must have no diagnosis, medication or authorisation field. The clinician-signature workflow is the authority for medical decisions.

04 · Vertical slice

One complete, clinician-supervised journey

OnboardingIdentity and notice
Profile + assessmentSource-linked evidence
Clinical safetyClear / Hold / Escalate
Clinical routingAssign queue only
Clinician reviewInvestigation + decision
Approval + pharmacyHuman signature + mock
Longitudinal timelineReproducible record

The decision may be to provide no treatment. Investigation results remain unreviewed until a clinician explicitly accepts them. A prescription is not submitted until an authorised signer and all applicable safety gates permit it. Unknown provider outcomes remain unknown and are reconciled before retry, rather than being inferred as success.

Essential invariant: An assessment, routing event, AI recommendation or UI button must never itself issue a prescription or clinically approve a treatment.
05 · Safety & reproducibility

Clinical rules, patient privacy and audit

The Framework's general-purpose configuration/rule facilities should be extended into a clinically governed evaluator. Each rule has an identifier, revision, effective period, authorising clinician, immutable digest, input schema and defined failure behaviour. Each rule evaluation stores the exact input snapshot and engine version; each signed treatment decision records the clinician, linked evidence and approval. Replaying a rule should reproduce the software evaluation, not replace the clinician's professional judgement.

RecordRequired immutable evidence
AssessmentForm version, patient/encounter IDs, input version, submitter, time
Clinical safetyRule bundle digest, input snapshot, hold decision, missing evidence, authorised override
RoutingQueue assignment reason, allowed reviewer/service, referral context
Treatment approvalReviewer identity, professional scope, decision, rationale, associated results, signature
PrescriptionSigned order, review evidence, provider ID, idempotency key and acknowledgements
TimelineSource reference, recorded/clinical time, prior record corrections and permissions

Start with fictional data only. Real patient data requires verified access policies, appropriate lawful basis and special-category condition, clinical purpose-of-access checks, data minimisation, safe retention, encrypted storage/key management, breach response, recovery testing, DPIA review and clinician safety sign-off. A local SQLite prototype is not proof of these controls.

07 · Copyable setup

GitHub repositories and submodule creation

The starter archive contains umicom-healthcare and umicom-healthcare-module as separate directories. Create and push them independently, then add only the module as a new application submodule in the existing superproject.

# Create the two remote repositories from independently committed local folders:
Set-Location "C:\umicom\Umicom-Healthcare-Starter\umicom-healthcare"
git init -b main
git add -A
git diff --cached --check
git commit -m "docs(healthcare): establish product scope and governance"
gh repo create umicom-foundation/umicom-healthcare --public --source . --remote origin --push

Set-Location "C:\umicom\Umicom-Healthcare-Starter\umicom-healthcare-module"
git init -b main
git add -A
git diff --cached --check
git commit -m "feat(healthcare): initialise safe C23 application module"
gh repo create umicom-foundation/umicom-healthcare-module --public --source . --remote origin --push

# Record the new independently versioned source as a pinned submodule:
Set-Location "C:\umicom\Umicom-Applications"
git submodule add -b main https://github.com/umicom-foundation/umicom-healthcare-module.git applications/healthcare

To enable builds, add the UMICOM_APPLICATIONS_BUILD_HEALTHCARE option and module registration to cmake/UmicomExtendedApplicationModules.cmake, preserving all existing code. The standard shared-host helper creates the umicom-healthcare GTK4 preview because the module has a umicom_healthcare_module target and a native_executable manifest entry.

cmake --preset windows-ucrt64-headless-debug -DUMICOM_APPLICATIONS_BUILD_HEALTHCARE=ON
cmake --build --preset windows-ucrt64-headless-debug --target umicom-healthcare-console healthcare-application-test --parallel 2
ctest --test-dir .\build\windows-ucrt64-headless-debug -R "^healthcare\." --output-on-failure

cmake --preset windows-ucrt64-debug -DUMICOM_APPLICATIONS_BUILD_HEALTHCARE=ON
cmake --build --preset windows-ucrt64-debug --target umicom-healthcare --parallel 2
Commit order: when shared Framework changes are made, commit and push Framework first, then Healthcare module, then commit the pinned submodule SHA(s) and CMake registration in the umicom-applications parent. The detailed file insertion locations and complete PowerShell guide are in the module repository's docs/REPOSITORY_SETUP.md.
08 · Assurance gates

What must be established before a pilot

The UK GDPR regards health data as special-category data. NHS England clinical risk management references DCB0129 for manufacturers and DCB0160 for deployment. The MHRA has software-as-medical-device qualification guidance based on intended purpose; a system can be regulated even without autonomous AI. HL7 FHIR defines interoperable healthcare resources and exchange interfaces, but full FHIR implementation is not necessary for the initial synthetic vertical slice.

Clinical release gate: No live patient data, diagnosis, prescription, provider submission or clinical deployment until the product's intended use and jurisdiction are approved, clinician-led safety management is completed, and applicable information-governance, security, professional and regulatory duties are met.

References: ICO guidance; NHS clinical safety; 2026 NHS standards review; MHRA; HL7 FHIR.
